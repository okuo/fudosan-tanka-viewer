# サイト横断・同一物件チェッカー 設計

作成日: 2026-07-11
状態: ユーザー承認済み

## 1. 背景

坪たんは、SUUMO、HOME'S、アットホーム、三井のリハウスの4サイトで、坪単価、月額コスト、修繕積立金、お気に入り、価格ウォッチ、Side Panel比較を提供している。

次の成長施策では、Chrome Web Storeで幅広い中古マンション購入検討者を獲得したい。ローン計算、お気に入り、価格追跡、CSV、Side Panelは競合拡張にも採用されており、既存機能の単純な増強だけでは差別化しにくい。

そこで、4サイト対応を直接的な強みに変える「サイト横断・同一物件チェッカー」を追加する。ユーザーが閲覧した物件をブラウザ内で照合し、同じマンションと同一住戸の掲載をまとめ、価格や掲載情報の差を表示する。

## 2. 目的

- 複数サイトで閲覧した同じマンションを自動的にまとめる。
- 同じマンション内の別住戸と、同一住戸の別掲載を区別する。
- 同一住戸について価格、月額費用、仲介会社、掲載状態などの差を比較する。
- 判定に自信がない組み合わせは候補として提示し、誤統合を防ぐ。
- ユーザーの手動統合・解除を学習し、以後の照合へ反映する。
- 外部通信や新しいChrome権限を追加せず、ブラウザ内で完結する。
- Chrome Web Storeで「4サイト横断・同一物件比較」を一目で訴求できる機能にする。

## 3. MVPの対象外

- 未閲覧サイトを自動検索または巡回すること。
- インターネット上の全掲載を網羅していると表示すること。
- 国土交通省API、地図API、独自サーバーを利用すること。
- 売出価格の妥当性や投資価値を断定すること。
- マンション名だけを根拠に自動統合すること。
- 閲覧した一般Webページの履歴を保存すること。

## 4. 基本体験

### 4.1 データの収集

対応4サイトの一覧ページまたは詳細ページを閲覧したとき、抽出できた物件情報をローカルの閲覧物件インデックスへ保存する。

初期版は閲覧済み・お気に入り登録済みの物件だけを照合対象にする。他サイトへの追加リクエストは行わない。

### 4.2 ページ上の表示

坪単価表示の近くに、照合結果がある場合だけ横断バッジを表示する。

- 高一致の同一住戸がある: `横断一致 3サイト`
- 中一致の候補がある: `同一候補 1件`
- 同じマンションの別住戸がある: `同じマンションに4住戸`
- 照合結果がない: バッジを表示しない

バッジを押すとSide Panelを開き、該当マンショングループを選択状態にして表示する。

表示文言は「他サイトにも掲載中」ではなく、「閲覧履歴内で他サイトの掲載を検出」とする。未閲覧サイトを検索していないことを明示する。

### 4.3 Side Panel

既存の「類似候補まとめ」を横断掲載の比較画面へ発展させる。最上位をマンション、その下を住戸、さらにその下をサイト別掲載とする。

```text
パークタワー晴海
├─ 48階・72.91㎡・3LDK
│  ├─ SUUMO     1億2,800万円  最安
│  └─ HOME'S    1億3,000万円  価格差あり
├─ 31階・68.42㎡・2LDK
│  └─ アットホーム 1億1,500万円
└─ 同一候補 1件
```

サイト別掲載には次を表示する。

- サイト名
- 価格と同一住戸内の価格差
- 管理費と修繕積立金
- 仲介会社
- 最終確認日時
- 掲載中、掲載終了の可能性、確認失敗
- 掲載ページを開く操作

同一住戸の最安掲載には `最安` を表示する。ただし、価格以外の条件が同一であることを保証する表現は使わない。

情報が食い違う項目には `記載差あり` を表示する。比較対象は価格、面積、間取り、階数、管理費、修繕積立金とする。

### 4.4 手動判定

中一致の候補には次の操作を表示する。

- `同じマンション`
- `同じ住戸`
- `別の物件`

手動判定はいつでも解除できる。手動判定は自動判定より常に優先する。

## 5. コンポーネント構成

### 5.1 `property-matcher.js`

新規の共有ロジックとして追加する。DOM、Chrome API、画面表示へ依存しない純粋関数を中心にする。

責務:

- マンション名、住所、間取り、階数などの正規化
- 文字列類似度の算出
- マンション一致スコアの算出
- 同一住戸一致スコアの算出
- 手動判定を加味したグループ生成
- 同一住戸内の掲載差分生成

`content.js`、`sidepanel.js`、`background.js` から利用できる形で読み込み、名前空間を1つだけ公開する。Nodeの軽量テストからも読み込めるよう、DOMを参照しない。

- content script: `manifest.json` で `property-matcher.js` を `content.js` より先に指定する。
- Side Panel: `sidepanel.html` で `property-matcher.js` を `sidepanel.js` より先に読み込む。
- service worker: `background.js` 冒頭の `importScripts()` で読み込む。

ES module化はMVPの範囲外とし、既存構成に合わせた通常スクリプトとして共有する。

### 5.2 `content.js`

責務:

- 既存のサイト別抽出結果から共通レコードを作る。
- 一覧ページでは複数レコードをまとめ、デバウンスして一括送信する。
- 詳細ページでは取得できる追加項目を既存レコードへ補完する。
- backgroundへ保存要求を送る。
- 現在ページの照合結果を受け、横断バッジを表示する。
- 照合機能の例外を既存機能から隔離する。

### 5.3 `background.js`

責務:

- 複数タブからの保存要求を直列化する。
- レコードのupsert、期限切れ削除、件数制限を行う。
- 保存後の照合結果を要求元へ返す。
- Side Panelを該当グループへ誘導するメッセージを中継する。

同時に複数タブが保存しても、古い読み取り結果による上書きでデータを失わないよう、保存処理をbackgroundへ集約する。

### 5.4 `sidepanel.js`

責務:

- 保存済みレコード、手動判定、確認済み名称別名を読み込む。
- マンション、住戸、サイト別掲載の階層を描画する。
- 価格差と記載差を表示する。
- 手動統合、解除、別物件指定を保存する。
- ページ上のバッジから指定されたグループを選択する。

### 5.5 `popup.js`

責務:

- 横断照合の有効・無効を設定する。
- 保存期間の説明を表示する。
- 閲覧物件データを全削除する操作を提供する。

## 6. 保存データ

### 6.1 `observedListingsV1`

```javascript
{
  version: 1,
  items: [
    {
      listingKey: "SUUMO:<source-id-or-canonical-url>",
      site: "SUUMO",
      sourceListingId: "optional",
      url: "https://...",
      pageType: "list | detail",
      rawName: "ザ・パークハウス新宿 中古マンション",
      rawAddress: "東京都新宿区...",
      normalizedBuildingName: "ザパークハウス新宿",
      normalizedAddress: "東京都新宿区...",
      buildingWing: "optional",
      roomNumber: "optional",
      priceMan: 12800,
      areaSqm: 72.91,
      layout: "3LDK",
      floor: 48,
      builtAt: "2019-02",
      totalUnits: 1076,
      buildingFloors: 48,
      managementFeeYen: 22000,
      repairFundYen: 15000,
      brokerageName: "optional",
      listingStatus: "active | possibly_ended | check_failed",
      firstSeenAt: "ISO-8601",
      lastSeenAt: "ISO-8601"
    }
  ]
}
```

`listingKey` はサイトとサイト固有IDの組み合わせを優先し、固有IDを取得できない場合はサイトと正規化済みURLを使う。同じ `listingKey` を再度確認した場合は新規追加せず、空でない新しい値で既存レコードを補完・更新する。

お気に入りかどうかは既存のfavoritesを正とし、整理時にURLで突き合わせる。閲覧物件側に重複したお気に入り状態を持たせない。

### 6.2 `listingMatchOverridesV1`

```javascript
{
  version: 1,
  buildingPairs: [
    { leftKey: "...", rightKey: "...", decision: "same | different" }
  ],
  unitPairs: [
    { leftKey: "...", rightKey: "...", decision: "same | different" }
  ]
}
```

ペアはキー順に並べて保存し、同じ組み合わせの重複を防ぐ。`different` は将来の自動再統合も禁止する。

### 6.3 `buildingAliasesV1`

手動確認されたマンション名の別表記を、街区住所へ限定して再利用する。

```javascript
{
  version: 1,
  entries: [
    {
      addressBlockKey: "東京都中央区晴海2-3-30",
      normalizedNames: [
        "パークタワー晴海クロノレジデンス",
        "パークタワー晴海クロノ棟"
      ],
      confirmedAt: "ISO-8601"
    }
  ]
}
```

次の条件をすべて満たす手動判定だけを別名学習へ反映する。

- ユーザーが `同じマンション` または `同じ住戸` を選んだ。
- 両レコードから街区までの住所を取得できた。
- 正規化後の街区住所が一致した。

住所が不足する場合は `listingMatchOverridesV1` のレコード間判定だけを保存し、名称別名には昇格させない。新しい掲載が同じ `addressBlockKey` を持ち、その名称が確認済み別名に含まれる場合、名称完全一致相当として採点できる。

`別の物件` というレコード間指定は、別名による一致より優先する。別名はユーザーが閲覧データを全削除したときに一緒に削除する。

### 6.4 `crossSiteMatchingSettingsV1`

専用の設定キーとして次を保存する。

```javascript
{
  enabled: true,
  retentionDays: 90
}
```

MVPでは保存期間の選択UIは設けず、90日固定とする。設定画面には期限を説明し、横断照合のON/OFFと全削除だけを提供する。

### 6.5 保持ルール

- 非お気に入りは最終確認から90日で削除する。
- 非お気に入りは直近500件まで保持する。
- お気に入りは90日制限と500件制限の対象外とする。
- 両方の対象レコードが削除された手動判定は整理時に削除する。
- 機能をOFFにしても既存データは自動削除しない。全削除は明示操作で行う。

## 7. 正規化

### 7.1 マンション名

次の順序で正規化する。

1. Unicode NFKC正規化を行う。
2. 英字を小文字へ統一する。
3. 全角・半角空白、中黒、括弧、装飾記号を除去する。
4. ローマ数字と一般的な漢数字の棟番号を算用数字へ統一する。
5. `west` / `ウエスト` など、限定した方角表記を共通トークンへ統一する。
6. `中古マンション`、`価格改定`、`新着`、`○階部分` など、サイト表示由来の語句を除去する。
7. 本体名と棟名を、取得できる場合は分離して保持する。

英語名と日本語名を無制限な辞書で同一視しない。代表的な表記変換は小さな明示リストに限定し、辞書だけで自動統合しない。

文字列比較には文字bigramのDice係数を使う。完全一致に加え、空白や接尾語の差を吸収する。短すぎる名前は類似度が過大になりやすいため、4文字未満では類似判定を使わず完全一致だけを見る。

### 7.2 住所

次を正規化する。

- Unicode NFKC正規化
- 都道府県、市区町村、町域、丁目、番地の区切り統一
- `一丁目` と `1丁目` の統一
- `1番2号`、`1番地2`、`1-2` の比較用表現への統一
- 建物名、階、部屋番号の除去

住所は完全一致キーに加え、市区町村・町域キーと街区キーを保持する。住所文字列の不足や表記差がある場合に段階的なスコアを付けるために使う。

### 7.3 ユーザー操作からの学習

手動判定は該当レコード間の強制判定として保存する。さらに、街区住所が双方で一致する場合だけ、確認済み名称を `buildingAliasesV1` へ追加する。住所キーでスコープを限定するため、同名マンションを別地域で誤統合しない。

将来、同じ街区住所と確認済み名称の組み合わせが再登場した場合は、名称完全一致相当として採点する。別名だけで住所点を補うことはなく、街区住所の一致を必須とする。

## 8. 照合ロジック

### 8.1 マンション一致スコア

| 判定材料 | 最大点 |
|---|---:|
| 住所 | 45 |
| 正規化マンション名 | 35 |
| 築年月 | 10 |
| 総戸数 | 5 |
| 建物階数 | 5 |

住所点:

- 街区まで一致: 45
- 町域まで一致し、街区の一方が欠損: 30
- 市区町村と町域だけ一致: 15
- 不一致または双方とも不足: 0

名称点:

- 正規化後に完全一致: 35
- Dice係数が0.85以上: 25
- Dice係数が0.70以上: 15
- それ未満: 0

補助項目は、双方に値があり一致した場合だけ加点する。不一致の場合は加点しないが、それ単独では別建物と断定しない。

判定:

- 80点以上: 高一致として同じマンションへ自動統合
- 60〜79点: 中一致として同じマンション候補
- 59点以下: 自動統合しない

住所が街区まで一致していない場合、合計が80点以上でも高一致へ昇格させず中一致に留める。マンション名だけで自動統合することはない。

### 8.2 同一住戸一致スコア

同じマンションと判定された掲載同士だけを住戸照合する。

| 判定材料 | 最大点 |
|---|---:|
| 部屋番号 | 強い判定条件 |
| 専有面積 | 45 |
| 階数 | 30 |
| 間取り | 15 |
| 向き | 5 |
| バルコニー面積 | 5 |

- 部屋番号が双方で取得でき、一致し、さらに専有面積差1.0㎡以内または階数一致のどちらかを満たす場合は高一致とする。
- 部屋番号だけが一致し、専有面積または階数で裏付けられない場合は中一致に留める。
- 部屋番号が双方で取得でき、不一致の場合は別住戸とする。
- 専有面積差が0.5㎡以内なら45点、1.0㎡以内なら25点、それ以上は0点とする。
- 階数、間取り、向き、バルコニー面積は双方に値があり一致または許容差内の場合だけ加点する。
- 価格はサイト間で異なる可能性があるため、同一判定には使わない。

判定:

- 80点以上: 高一致として同一住戸へ自動統合
- 55〜79点: 中一致として同一住戸候補
- 54点以下: 別住戸として扱う

棟名が双方で取得でき明確に不一致の場合、住戸スコアに関係なく別棟として扱う。ただし、手動判定はこの規則より優先する。

## 9. データフロー

```text
対応サイトの一覧・詳細ページ
  → サイト別情報抽出
  → 共通レコード化
  → 一覧はデバウンスして一括送信
  → backgroundの直列upsert
  → 期限・件数整理
  → matcherで照合
  → 保存元タブへ結果返却
  → ページバッジ更新

Side Panel
  → 保存済みレコード、手動判定、名称別名を読み込み
  → matcherでグループ生成
  → マンション / 住戸 / 掲載の階層を描画
```

一覧ページのMutationObserverで同じカードを繰り返し検出しても、`listingKey` によるupsertと送信前の重複除去で保存回数を抑える。

## 10. エラー処理

- 名前または住所が不足するレコードは保存できるが、自動マンション統合には使わない。
- 一部項目が取れない場合も、取得できた項目だけを保存する。
- 照合処理の例外は捕捉し、坪単価、お気に入り、価格ウォッチ、CSVへ伝播させない。
- 保存容量不足時は、期限切れ非お気に入り、古い非お気に入りの順で整理して1回だけ再試行する。
- 再試行にも失敗した場合は新規閲覧記録を破棄し、既存保存データを維持する。
- サイトのHTML変更で抽出できない場合、そのサイトの新規記録だけを停止し、他サイトと既存データは維持する。
- 手動判定データが不正または参照先を失っている場合は無視し、次の整理時に削除する。
- Side Panelの対象グループが既に削除されている場合は、通常の比較画面を表示して短い案内を出す。

ログは既存サイト別プレフィックスを使い、横断照合であることが分かるメッセージを追加する。通常利用時に大量出力しない。

## 11. プライバシー

- 保存するのは対応サイトから抽出した物件情報と確認日時だけとする。
- 一般の閲覧履歴、検索語、ユーザー識別子は保存しない。
- データは `chrome.storage.local` に保存し、外部送信しない。
- 横断照合は初期状態ONとする。
- ポップアップからOFFと全削除を選べるようにする。
- 全削除では閲覧レコード、手動判定、確認済み名称別名をまとめて削除する。
- 更新後のWhat's Newで、対応サイトの物件情報を横断照合のためローカル保存することを明示する。
- 機能追加時に `PRIVACY_POLICY.md`、`PRIVACY_PRACTICES.txt`、`STORE_LISTING_TEXT.txt` を更新する。
- Chrome Web Storeのデータ利用申告で、保存するWebサイトコンテンツの用途を正確に説明する。

## 12. テスト

### 12.1 純粋関数

- 全角・半角、空白、中黒、括弧、英字大小、ローマ数字、漢数字の正規化
- `WEST` / `ウエスト` など許可した表記変換
- サイト固有の装飾文言除去
- 住所の丁目・番地表記統一
- bigram Dice係数と短い名称の例外
- マンションスコアの60点・80点境界
- 住戸スコアの55点・80点境界
- 街区住所が一致する手動統合からの名称別名作成
- 住所不足時に名称別名を作成しないこと
- 確認済み名称別名が別地域へ適用されないこと

### 12.2 誤統合防止

- 同じ名前で住所が異なるマンション
- 同じ市区町村にある同名マンション
- 同じマンションの別棟
- 同じマンション、近い面積、異なる階の住戸
- 同じ階・間取りだが面積が異なる住戸
- 価格だけが一致する別住戸
- 情報が不足する一覧レコード

### 12.3 保存処理

- 同じ `listingKey` の更新
- 空値で既存値を消さないこと
- 一覧と詳細のデータ統合
- 複数タブからの連続一括upsert
- 90日経過データの削除
- 非お気に入り500件制限
- お気に入りの期限・件数制限除外
- 参照先を失った手動判定の整理
- 全削除による閲覧レコード、手動判定、名称別名の一括削除
- 容量不足時の整理と1回再試行

### 12.4 サイト別フィクスチャ

4サイトそれぞれについて、一覧と詳細から共通レコードが作られることを確認する。住所、マンション名、面積、階数、間取りの最低限を重点項目とする。

### 12.5 E2E

1. SUUMOの物件を閲覧する。
2. HOME'Sで同じマンションの同一住戸を閲覧する。
3. `横断一致 2サイト` が表示される。
4. バッジからSide Panelを開く。
5. 同一住戸内に2掲載と価格差が表示される。
6. 中一致データを手動で統合・解除する。
7. Side Panelを再読み込みしても判定が残る。
8. 横断照合をOFFにすると新規保存とバッジ表示が止まる。
9. 全削除後に閲覧グループと手動判定が消える。

既存の軽量テストとChrome拡張E2Eもすべて実行し、回帰がないことを確認する。

## 13. 成功条件

- 自動統合用の代表テストデータで誤統合が0件である。
- 情報不足または曖昧なデータが自動統合されない。
- 4サイトの一覧・詳細フィクスチャから共通レコードを生成できる。
- 複数タブから同時に記録してもデータを失わない。
- 外部通信と新しいChrome権限を追加しない。
- 既存の坪単価、お気に入り、価格ウォッチ、Side Panel、CSVに回帰がない。
- Chrome Web Storeのスクリーンショット1枚で、同一住戸の複数サイト掲載と価格差を説明できる。
